# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Revforge simule en temps réel une voiture et le son de son moteur, tous deux configurables : un cœur C++20 sans dépendance, joué dans le navigateur via WebAssembly, ou rendu en WAV en ligne de commande. Les commentaires, les noms de tests et les messages de commit sont en français ; les identifiants, la CLI et le texte par défaut du site sont en anglais.

## Commandes

Il faut CMake, Ninja, Python 3 (génération des préréglages), GCC ou Clang (les options de déterminisme de `CMakeLists.txt` sont les leurs) et, pour le WASM, Emscripten et Bash. Si `node`/`npm` sont introuvables, charger Emscripten, qui les fournit : `source ~/emsdk/emsdk_env.sh`. `scripts/build_wasm.sh` lit aussi `EMSDK` s'il est installé ailleurs.

```bash
# Natif (ctest ne recompile pas : toujours construire avant)
cmake -S . -B build -G Ninja && cmake --build build
ctest --test-dir build --output-on-failure
ctest --test-dir build -R golden_                  # empreintes seules
./build/revforge_tests -tc="pas de clic*"          # un test doctest

# WebAssembly (compile et copie vers web/public/revforge.wasm, ignoré par git)
scripts/build_wasm.sh
node tools/check_wasm.mjs build-wasm/revforge.wasm build/revforge-render

# Site, depuis web/
npm ci
npm run dev
npm run check                                      # svelte-check, seul contrôle de types
npm run build && npx playwright test               # une première fois : npx playwright install chromium firefox
npx playwright test -g "exporte un WAV valide" --project=chromium
```

`revforge_tests` dure plusieurs minutes, les empreintes moins d'une demi-minute. Un filtre doctest qui ne trouve rien affiche quand même `Status: SUCCESS` : regarder `test cases`. Sous Windows, un filtre accentué ne trouve jamais rien : mettre un joker à la place du mot accentué.

Playwright teste `vite preview`, donc `web/dist` : sans `npm run build` (et `scripts/build_wasm.sh` si le C++ a changé), il teste l'ancienne version. Il réutilise aussi un serveur déjà lancé sur le port 4173 (`REVFORGE_PW_PORT` en choisit un autre).

La CI (`.github/workflows/ci.yml`) enchaîne tout cela sous Ubuntu. `pages.yml` publie le site à chaque push sur `main`, sans attendre la CI, dans un sous-dossier, d'où `base: './'` dans `vite.config.ts`. L'`AudioWorklet` n'existe qu'en contexte sécurisé : `web/index.html` redirige le HTTP vers le HTTPS, sauf en local et sur une adresse IP, et un téléphone sur `http://<IP>` n'a donc pas de son.

Pour la consommation, sans rendre de son : `./build/revforge-render --out none --preset city_14 --scenario wltc --fuel 1` (aussi `cruise --kmh 90` et `idle`). `--fuel` se lit à sa valeur : `0` ou `1`, cet affichage ; `petrol` ou `diesel`, le carburant d'un moteur donné en entier (ignoré sur un `--preset`, comme le reste du moteur). Pour le creux de reprise d'un carburateur : `--out none --carb single --scenario tipin --rpm 1500`. Pour la mise en température : `--out none --preset city_14 --scenario wltc --start cold --fuel 1 --thermal t.csv` (`--ambient` pour l'air). Pour la carte d'avance et la marge au cliquetis, régime par régime : `--out none --preset city_14 --compression 13 --scenario steady --seconds 1 --knock 1` (`--trace` écrit aussi l'avance, la limite et ce que retire le capteur). Pour l'air de charge : `--out none --preset hot_hatch_turbo --intercooler water --scenario soak --fuel 1` (la charge et la boucle d'eau départ après départ, puis la ligne « Charge air » ; `--trace` en écrit aussi les colonnes).

Pour écouter ou comparer un rendu : `./build/revforge-render --list`, `--help` pour les options, `--scenario turbo` pour le retard (avec `--preset`, seuls `--layout` (sur les cylindres du préréglage), `--exhaust`, `--routing`, `--supercharger`, `--antilag`, `--turbo-pipe`, `--cam`, `--filter`, `--carb` (ou `--fuel-system`), les réglages du socle moteur (`--help`, de `--cycle` à `--start`), l'emplacement, l'isolation, les vitres et les options de boîte s'appliquent, celles-ci remplaçant toute la boîte du préréglage, et `--stroke`, sur l'alésage et les cylindres du préréglage ; le reste est ignoré : donner tout le moteur pour changer `--turbo`), `tools/compare_wav.py a.wav b.wav`. Pour mesurer un rendu face à de vrais moteurs : `tools/analyze_sound.py --png sortie.png a.wav b.wav` (numpy, scipy et matplotlib requis) ; regarder le spectrogramme, car un spectre moyen ne révèle pas un défaut temporel. Pour un sifflement de boîte : `tools/analyze_gearbox.py fichier.wav:début:fin:f1min:f1max`. Pour les rangs d'un régime tenu, en ordres de l'arbre : `tools/analyze_orders.py --rpm 4000 a.wav b.wav`.

## Architecture

Une seule simulation, `core/`, trois façons de l'appeler : `cli/render.cpp`, `tests/`, et `wasm/exports.cpp`, une interface C à état global (`rf_*`).

- `EngineSound` (`core/src/engine_sound.cpp`) : le son, échantillon par échantillon, à partir d'un `EngineProfile`, d'un régime et de `setDrive` (remplissage, turbo, coupure). Sans `setDrive`, la charge se déduit de la pente du régime, chemin utilisé par les tests et `--scenario steady`. Le modèle acoustique et sa calibration sont décrits dans `docs/modele.md`.
- `SoundField` et `CabinPath` (`core/src/acoustics.*`) : de la voiture à l'oreille. Les sources (`Source`) arrivent en pascals, à 1 m d'elles, placées par `carAcousticsOf` ; le chemin (directivité, caisse, air, retard, sol, tête ou parois) découle de ce plan, sans gain saisi par position. `SoundSheet` (`sound_sheet`) : les niveaux de fiche d'un réglage. Voir « D'où l'on écoute » dans `docs/modele.md`.
- `Architecture` (`architecture`) : l'ordre d'allumage, la culasse, la rangée et le rang de chaque cylindre, d'où les intervalles et les manetons ; jusqu'à 16 cylindres (`kMaxCylinders`), VR et W compris. Seuls les VR, les W et plus de 12 cylindres en tirent leur son (`ownArchitecture`, `applyArchitecture`) ; les autres gardent le calcul d'origine. C'est là qu'on lit les culasses (`head`, `headShare`) et les intervalles (`firingDeg`, `intervalAfterDeg`). Voir « Les architectures » dans `docs/modele.md`.
- `Powertrain` (`powertrain`) : `EngineConfig`, `CarConfig` et électrique ou non. C'est la source des courbes de couple, de la démultiplication et des performances ; rien de tout cela n'est saisi à la main.
- `GearboxConfig` (`gearbox`) : la boîte comme pièce, indépendante du moteur. `designGearbox` en tire les dents, les rapports, les inerties et le couple admissible ; `gearingOf` l'adapte à la voiture si le pont n'est pas choisi. Son bruit est `GearboxSound` (`core/src/gearbox_sound.cpp`) : des forces sur les roulements, à travers le carter, à partir de `GearboxDrive`. Il suit les arbres, jamais le régime du moteur, a son propre générateur, et reste muet sans `setGearbox`. Voir « La boîte » dans `docs/modele.md`.
- `ValvetrainParts` et l'affolement (`valve_float`) : les pièces de chaque distribution ramenées à la soupape, le ressort d'origine dimensionné pour la zone rouge, le régime d'affolement (`valveFloatRpm`) et ce qui se passe au-delà : remplissage (`valveFloatShare`, dans `breathing`), frottement de came des culbuteurs et des ressorts raides. Le son le reçoit par `EngineProfile::valves` ; ses deux bruits, le choc des poussoirs et le siège qui claque, sont `ValvetrainSound` (`core/src/valvetrain_sound.cpp`), chacun à son générateur, muets sans leur cause. Voir « Les culbuteurs et l'affolement » dans `docs/modele.md`.
- `Carburetor` (`carburetor`) : un col et une pipe communs, ou un corps par cylindre, selon `FuelSystem`. `carburetorDropPa` donne la perte de charge, appliquée dans `breathing` ; `Carburetor::step` suit le carburant (colonne, pompe, film x-τ) à chaque pas de `DrivingModel`, et renvoie la part du couple que permet le mélange. Tout cela ne s'exécute pas sur une injection, ni sur un diesel, qui l'ignore. Voir « Le carburateur » dans `docs/modele.md`.
- `TurboCharger` (`turbo`) : l'arbre du turbo, intégré à chaque pas de `DrivingModel` par son bilan de puissance, sans constante de temps de retard. `boost()` est la pression réelle avant le papillon, en part de `boostBar`, et `torqueCurveNm` en est l'équilibre (`turboSteady`). Le son le reçoit par `setTurbo` ; le gaz (`fluidGas.ts`) en suit le rapport de pression et la sortie du compresseur. Sur un moteur sans turbo, rien de tout cela ne s'exécute. L'anti-lag (`anti_lag.cpp`) ne change que ce qui arrive à la turbine, pied levé, sur un turbo à essence ; `--trace` en écrit les chiffres.
- `BoostController` (`boost_control`) : la régulation de pression d'un turbo. Le ressort (`spring`, défaut) reste dans `TurboCharger`, au bit près ; `electronic` et `by_gear` commandent la membrane par `TurboInput::gateDemand` (électrovanne découpée, PID discret réglé au banc par SIMC, cible absolue, plafond de couple par rapport). Pures et réutilisables pour d'autres turbos : `boostTargetPa`, `springGateDemand`, `gateForVacuum`. Voir « La régulation de pression » dans `docs/modele.md`.
- `TwinTurbo` (`twin_turbo`) : deux turbos en parallèle ou en séquence, le twincharger (un compresseur mécanique en amont du turbo, avec embrayage et volet) et la géométrie variable, choisis par `turboLayout` et `variableGeometry` (`usesTwinTurbo`). Le turbo simple à soupape reste `TurboCharger`, au bit près. Chaque arbre a son bilan de puissance, avec les lois de `turbo.cpp` et de `supercharger.cpp` appelées par un renvoi (`turbo_laws.hpp`, `supercharger_laws.hpp`) : on n'y recopie rien. Les compresseurs soufflent dans un volume commun ; `twinTurboSteady` en est l'équilibre, branché sur `torqueCurveNm`, `steadyBoost` et `intakeDropPa`. `DrivingModel::turboState()` est le premier arbre (ou le turbo simple), `turboStateB()` le second ; le son reçoit le second par `setTurboB`, à son propre générateur, et le gaz à l'écran a alors deux turbines et deux chemins d'air. Voir « Deux turbos, twincharger et géométrie variable » dans `docs/modele.md`.
- `Supercharger` (`supercharger`) : le compresseur mécanique, à un rapport fixe du vilebrequin. Un volume entre lui et le papillon, sans arbre à lancer ; `superchargerSteady` en est l'équilibre, et ce qu'il prend au vilebrequin se paie à part (`driveNm`). Il passe par les mêmes `rf_turbo_charge`, `rf_turbo_out_c`… que le turbo. Son bruit est `SuperchargerSound` (`core/src/supercharger_sound.cpp`) : des poches qui se vident, à son propre générateur.
- Le deux-temps (`two_stroke`) : `EngineCycle::TwoStroke`, une explosion par tour, des lumières calées par leur hauteur (bielle et manivelle), un carter qui pompe. `twoStrokeCycle` intègre carter, transferts, cylindre et l'onde de la ligne à la lumière (tubes de Kelly et Lochbaum, `lineStretches` d'`exhaust_line.cpp`) ; `twoStrokeFullLoad` en garde une table par moteur (mémoire statique de quatre moteurs), d'où le couple (`twoStrokeIndicatedBar`), le balayage à charge partielle et les ratés (`twoStrokePartLoad`, `twoStrokeFiring`) que lisent `DrivingModel` et `ConsumptionMeter`. La chambre de détente (`Exhaust::Expansion`) est accordée sur le moteur (`expansionChamberFor`) et sa réponse se calcule depuis sa géométrie (`ExhaustLine::computeExpansion`). Dans le son, deux explosions par cylindre en deux tours (comme le rotatif) et des ratés à leur propre générateur. Un deux-temps est essence, atmosphérique, d'au plus 6 cylindres : `coherentTwoStroke` (CLI, WASM) et `coherentConfig` (site). Voir « Le deux-temps » dans `docs/modele.md`.
- `DrivingModel` : intègre à pas fixe de 1 ms le couple, l'inertie, l'embrayage, la boîte et les pneus. Il pilote le son avec le régime *réel* du moteur. Sa logique de passage (`shift_logic.cpp`, fonctions pures) et ses trajets (`driver_scenarios.cpp`, des données) sont à part : `docs/modele.md`. Le mode normal et le trajet `City` sont la logique d'origine, au bit près : le mode normal sur route plate ne passe pas par `decideShift`. `EngineProfile::fromCarRpm` et `revMultiplier` ne servent plus qu'à une source de régime externe (bus CAN) : le site et les scénarios modélisés ne les utilisent pas.
- Le calculateur (`ecu`) : la carte d'avance et de richesse en fonctions pures (`demandedAdvanceDeg`, `demandedLambda`, `ecuFullLoadShare`…), appliquée au couple de pleine charge, à la consommation, au gaz de la turbine et au son ; le rupteur progressif ou à coupure d'allumage, le launch control, le passage à fond et l'antipatinage décidés à chaque pas de `DrivingModel` (`stepEcu`, `finishEcu`, `EcuAction`), et `EcuDrive` pour le son (`setEcu`). Rien ne s'exécute au défaut. `--scenario launch_control` mesure un départ arrêté. Voir « Le calculateur » dans `docs/modele.md`.
- `ConsumptionMeter` (`consumption`) : essence, huile ou énergie, intégrées à chaque pas de `DrivingModel` à partir de ce que fait le moteur (bilan d'énergie, `docs/modele.md`, « La consommation »). Il lit le couple et ne renvoie rien vers la physique : la masse ne baisse pas, le son ne change pas.
- `AmbientAir` (`atmosphere`) : l'air du jour, de `ambientC` et `altitudeM` (pression ISA, masse volumique, vitesse du son, absorption). L'air piégé (`ambientChargeShare`, `trappedAirK`) change le couple indiqué, la traînée suit σ, le son se propage et rayonne dans cet air. Voir « L'air ambiant » dans `docs/modele.md`.
- `ThermalNetwork` (`thermal`) : métal, eau côté moteur, eau du radiateur et huile, intégrés par `DrivingModel` toutes les 10 ms à partir de l'énergie du carburant (la fonction pure `ConsumptionModel::fuelGps`, pas le compteur) et des frottements. Il agit toujours, parti chaud ou froid, par l'écart de l'eau et de l'huile à la référence chaude (eau 90 °C, huile 100 °C), exactement nul quand elle est atteinte : frottements (négatifs au-delà de 100 °C), ralenti visé et enrichissement (sous 70 °C d'eau), film de carburant, air piégé (la paroi suit l'eau), carte du cliquetis. Un échangeur eau-huile tient l'huile vers 95 à 102 °C. `holdThermalReference` le tient à la référence, pour les essais seulement. Ses fonctions pures (`oilViscosityPaS`, `coldFrictionNm`, `frictionFactor`, `coldIdleRise`, `coldEnrichment`, `wallHeatShare`) sont là pour la combustion, l'injection et le calculateur. La fiche (`measurePerformance`) se mesure moteur chaud. Rien de tout cela sur l'électrique. Voir « La thermique » dans `docs/modele.md`.
- `combustion` : le taux de compression (rendement, démarreur, détente), les carburants (`fuelProperties`) et le cliquetis (Douaud-Eyzat, Livengood-Wu, sur un cycle à une zone tabulé dans `KnockMap`). `DrivingModel::stepKnock` en tire le capteur et le couple, `KnockSound` (`core/src/knock_sound.cpp`, son propre générateur) la résonance de la chambre, reçue par `setKnock`. Rien ne s'en exécute tant que `combustionStock` et `knockConditionsStock` sont vrais : voir « La combustion » dans `docs/modele.md`.

Côté site, `web/src/lib/engine.ts` instancie **deux exemplaires** du même WASM : l'un dans l'AudioWorklet (`web/public/worklet.js`, JS pur, ni compilé ni typé) pour le son, à 48 kHz quelle que soit la carte son (`SIMULATION_RATE` : le simulateur n'est pas invariant en fréquence d'échantillonnage) ; l'autre sur le thread de la page pour la fiche technique (`Engine.spec`) et l'export WAV, à 44,1 kHz. La page pilote le worklet par messages, et il renvoie sa télémétrie à 30 Hz. Les vues animées (`CarStage`, `EngineView`, `ExhaustView`, `GearboxView`) sont des canvas qui partagent une seule horloge, `Motion` (`web/src/lib/motion.ts`), réglée sur la télémétrie : ralenti réglable (`motion.slow` : 12 par défaut, 4, ou 1 pour le temps réel), proportionnel au vrai régime et sans plafond, une bouffée par explosion dans l'ordre d'allumage. Une nouvelle animation lit cet état au lieu d'avoir sa propre horloge.

La couleur du thème est une chaleur : `web/src/lib/heat.ts` traduit la température des parois (`Motion.heat`, temps réel, jamais celle du gaz, qui suit le ralenti) en `--heat`, `--heat-text`, `--on-heat`, à 8 Hz au plus et sur les seuls éléments marqués `use:heated`, jamais sur la racine. Le reste de la page reste neutre et se sépare par le ton, sans bordure ; une voiture électrique garde une couleur froide fixe, sans chaleur inventée.

La page est un tableau de bord sur toute la largeur (`App.svelte`) : poste de conduite à gauche (`Tachometer`, démarrage, pédales, modes), voiture et une seule vue à la fois au centre, jauges à droite (`GaugeBank`, `PowerCurves`, `LevelMeter`), `Dynamics`, `Trends` et `Spectrum` dessous, `ChartsPanel` à la demande. Sur téléphone, le démarrage et les pédales se collent au bas de l'écran. Une vue (`EngineView`, `ClutchView`, `GearboxView`, `ExhaustView`) est montée la première fois qu'on la demande, puis cachée et en pause. Les réglages sont dans des volets (`Panel.svelte`, un `<dialog>` non modal ouvert par `show()`) : le reste de la page reste vivant, et les pédales restent cliquables. Ils restent montés quand ils sont fermés, donc ce qui lit la télémétrie à l'intérieur reçoit `IDLE_TELEMETRY` ou 0 volet fermé. Une jauge n'est jamais un composant rendu à 30 Hz : `Gauge` et `Meter` écrivent dans le DOM via une `InstrumentClock` (`lib/instruments.ts`), seulement ce qui a changé. Ils lisent `Readings`, qui lit la télémétrie et le modèle du gaz ; `motion.update(…, false)` sert aux jauges qui n'ont pas besoin du gaz, pour qu'il ne soit calculé que si une vue ou une jauge qui le montre est à l'écran. Animations coupées, `Motion.meters` fait avancer un réseau à part pour ces jauges, sans panache ni particules. Une jauge ne montre que ce que la simulation calcule : rien d'inventé.

La vue de la boîte (`GearboxView`) a trois couches sans DOM ni WebGL, testées sans navigateur : `gearboxModel.ts` (quelles pièces, où, comment elles tournent, à partir de `BoxSpec`), `gearboxGeometry.ts` (maillages : dentures en développante, hélice), puis `gearboxPaint2d.ts` et `gearboxScene.ts` pour dessiner le même état en coupe 2D ou en 3D. Le primaire vient de `Motion` et tout le reste s'en déduit par les dents, ce qui garde les paires en prise. Une automatique y est un schéma, le simulateur n'ayant pas de train épicycloïdal.

`EngineView` dessine en 3D (three.js, chargé à la demande par `render3d.ts`) ou en écorché 2D (`engine2d.ts`) le même moteur : `engineLayout.ts` déduit de l'ordre d'allumage et de l'architecture la place de chaque cylindre et les angles du vilebrequin, `EnginePose` calcule à chaque image ce que lisent les deux vues, `turboChain.ts` place pour elles le chemin de l'air d'un turbo, `engineScene.ts` construit les pièces 3D. `mesh3d.ts` génère les maillages, sans dépendance ; `threeSubset.ts` liste ce que le site utilise de three.js, pour que le reste ne soit pas livré. Sur un rendu logiciel, `render3d.ts` remplace le PBR par des matcaps et le verre par des arêtes. Un rotatif a ses propres pièces, sans rien de tout cela : `rotary.ts` (géométrie, `RotaryPose`, testés sans navigateur), `rotary2d.ts`, `rotaryScene.ts`. `GasNetwork` y calcule trois chambres par rotor, sur 1080°.

Le texte du site passe par `web/src/lib/i18n.svelte.ts` : `t`, `whole` et `fixed` suivent la langue courante (anglais par défaut, français au choix, jamais celle du navigateur), en direct dans les gabarits et à chaque image dans les canvas, sans jamais toucher au son.

Le gaz à l'écran (`web/src/lib/fluid*.ts`) est un vrai calcul, mais pour l'affichage seulement : il suit `Motion`, en temps physique divisé par `motion.slow`, et n'agit jamais sur le son. `GasNetwork` (`fluidGas.ts`) : Euler quasi-1D à section variable pour les tubes (volumes finis, flux HLLC), bilans à zéro dimension pour les cylindres (remplissage et vidange, combustion de Wiebe) et les volumes de jonction. `FluidField` (`fluidField.ts`) : stable fluids 2D, pour le panache et la recirculation dans les volumes, pilotés par l'état du réseau. `GasFlow` (`fluid.ts`) assemble le tout avec les particules, la qualité adaptative et le sommeil moteur coupé ; `GasPainter` (`fluidRender.ts`) dessine. Rien de cela n'utilise WebGL. L'embrayage (`ClutchView`) lit la télémétrie, avec son échauffement dans `Motion` : `clutchMechanism.ts` calcule sans rien dessiner la chaîne pédale, hydraulique, fourchette, butée, diaphragme, plateau, et la bague de la butée (`Motion.releaseRace`) ; `clutchSection.ts` donne en millimètres les profils que `clutchDraw2d.ts` coupe et que `clutchScene3d.ts` tourne, sur la scène de `render3d.ts`. La levée du plateau est dessinée agrandie (`LIFT_EXAGGERATION`, indiquée à l'écran), jamais calculée ainsi. Les graphiques (`ChartsPanel`) ne sont montés que panneau ouvert ; `history.ts` remplit en permanence un anneau de mémoire fixe.

## Invariants

**Déterminisme au bit près.** Natif et WASM produisent le même son, vérifié par `check_wasm.mjs`. La parité avec la version Kotlin d'origine (CANCitroen) a été abandonnée volontairement lors de la refonte du son. Dans le son, passer par `revforge::km` (`core/src/kotlin_math.hpp`, calcul en `double` arrondi en `float`) et garder conscience de l'ordre des appels à `random()` : ajouter un tirage décale tout le son qui suit, donc les empreintes. Dans `DrivingModel`, passer par `revforge::portable` (`core/src/portable_math.hpp`) plutôt que par les fonctions de la bibliothèque mathématique autres que `sqrt` : leurs résultats diffèrent d'un dernier bit entre plateformes, et cet écart s'amplifie jusqu'à décaler un passage de rapport.

**Changer le son est un choix.** Les tests `golden_*` de `CMakeLists.txt` comparent un hachage du rendu 16 bits. Si un changement est voulu, reprendre la nouvelle valeur affichée par `revforge-render --out - <arguments du test>` et la mettre à jour ; sinon, c'est une régression. Modifier un préréglage utilisé par ces tests change aussi leur empreinte. Les mesures spectrales ne suffisent pas à valider un son : l'écoute tranche, et il faut le signaler quand elle reste à faire. Un test de son doit être contre-éprouvé en retirant ce qu'il protège : c'est ainsi qu'un premier test anti-« fermeture éclair » s'est révélé aveugle.

**Tout ce qui ne vient pas de l'échappement garde sa place à bas régime.** L'échappement varie beaucoup avec la charge ; une source à niveau fixe (soupapes, par exemple) passe devant dès qu'il se fait discret. C'est ainsi qu'est né le défaut « métal qui claque ». De même pour un souffle : à pleine bande et à niveau presque fixe, il reste derrière le moteur comme un bruit blanc, d'où `kNoiseTopHz`. Le comparateur ne voit pas ce défaut : mesurer la bande 8-16 kHz face à 500-2000 Hz, et se méfier des références, dont un « ralenti » s'est révélé être un moteur coupé. Un nouveau bruit a sa place sur la voiture : `stem(Source::…)`, en pascals à 1 m, à un seul endroit.

**Le niveau est physique, de bout en bout.** La réponse de la ligne n'est pas normalisée, et aucun réglage ne compense d'une position ou d'un échappement à l'autre : c'est ainsi qu'une ligne directe avait fini moins forte qu'une ligne d'origine. Une ligne, une isolation ou une position qui changent le niveau doivent le faire par leur géométrie ; seul `toneGain`, après le sonomètre, ramène le niveau réel vers la sortie. Le dB(A) affiché est lu avant le volume, et reste une estimation, jamais présentée comme mesurée. Tenir aussi `tests/acoustics_test.cpp` face aux valeurs publiées : ne pas corriger un écart de niveau en touchant à une formule.

**Pour un bruit mécanique, partir d'enregistrements et de la cause.** Le démarreur a été rejeté cinq fois à l'écoute alors que rythme et spectre moyen étaient justes : sinusoïdes (« vaisseau »), chocs aléatoires sur résonances molles (« cailloux »), frottement sur résonances fines (« ballon en latex »), note forte qui glisse à volume constant (« DJ qui fait drifter un CD »). Des sons générés (ElevenLabs) peuvent servir de référence d'écoute, jamais de son livré : le son du site reste simulé. Il est calé sur de vrais démarrages (`tools/analyze_starter.py`, `docs/modele.md`) : couple transmis calculé par `compressionLoadNm`, et dans `StarterSound` (`core/src/starter_sound.cpp`) un bruit de contact selon le couple, des balais selon le courant et des chocs d'engagement, le tout passé dans une réponse dense propre au moteur. Comparer des spectrogrammes en fenêtres courtes : une longue fenêtre cache les raies qui ondulent.

**Le timbre ne suit pas le régime.** La ligne (`ExhaustLine`, réponse calculée depuis sa géométrie, convolution partitionnée) est fixe : ce sont les harmoniques qui défilent devant. Tout le gaz la traverse. Les raies doivent s'effacer progressivement vers les aigus sans disparaître : de 8,7 à 17,1 dB entre 1,5 et 3,5 kHz sur de vrais moteurs. Trop, c'est la « fermeture éclair » ; trop peu, c'est du bruit sans moteur (`tools/perceptual_compare.py`).

**La consommation lit, elle n'écrit pas.** Aucun chiffre de consommation ne revient vers le couple, la vitesse ou le son. Ne pas régler un préréglage pour coller à un chiffre publié : l'écart se montre dans le tableau de `docs/modele.md`. L'huile consommée reste un ordre de grandeur, à un facteur trois près. Les températures d'eau, d'huile et de métal sont calculées par le réseau thermique (`ThermalNetwork`) ; le niveau et la pression d'huile restent hors champ tant qu'ils ne découlent de rien de réel.

**Temps réel.** `EngineSound::render` n'alloue pas et ne prend aucun verrou (vérifié par un test via `operator new`, dans `tests/main.cpp`). Le résultat ne dépend pas de la taille des blocs : tout état doit évoluer par échantillon, pas par bloc.

**Contraintes du WASM.** Pas d'exceptions ni de RTTI, 4 Mo de mémoire sans croissance, et aucun import : le worklet instancie le module avec `{}`, donc une fonction qui tire un import système casse le chargement.

**Le gaz à l'écran n'alloue pas.** Viser moins de 4 ms par image pour tout le fluide. Dans `fluid*.ts`, jamais de nombre à virgule en argument d'une fonction que le compilateur ne déplie pas, ni de `let` de module : cela alloue un objet par appel, 85 ko par image sur une première version. Passer par les tableaux (`riemann`, `flux`, `orifice`, `reservoir`) et les champs de la classe. Les pas de calcul lisent leurs entrées dans `FrameInputs`, recopié une fois par image : lus sur des objets de formes diverses, ses nombres sont recopiés à chaque lecture (3 ko par image de plus, et `interface.spec.ts` échouait en CI une fois passés les tests de nouveaux réglages). Un test mesure le tas, dans l'état où l'ont laissé les spécifications précédentes : en lancer une seule ne suffit pas. Un test de physique compare aussi une onde au coefficient de réflexion théorique : ne pas remplacer le calcul des changements de section (`stepAreaChanges`) par un flux direct entre cellules, qui invente 0,3 bar de contre-pression par volume.

- **Télémétrie thermique** : `rf_coolant_c`, `rf_oil_c`, `rf_metal_c`, `rf_thermostat`, `rf_fan`, `rf_oil_viscosity`, `rf_cold_friction_nm`, `rf_cold_idle_rpm`, `rf_cold_enrichment`, `rf_warm_friction_nm` dans `exports.cpp`, `EXPORTED_FUNCTIONS`, `RfExports`, `Telemetry`/`IDLE_TELEMETRY` et `worklet.js` ; `coolantC`/`oilC` dans `Readings`, qui affiche avant le premier son la référence chaude (90 et 100 °C, recopies de `kWarmCoolantC` et `kWarmOilC`) ou l'air ambiant ; `coolant_c` et `oil_c` dans la ligne `raw` de `--fuel 1`, comparés par `check_wasm.mjs`. Une nouvelle coupure de combustion ou une nouvelle source de frottements dans `updateEngine` renseigne aussi `frictionHeatNm_`, la chaleur que reçoit le réseau.
- **Entre les sujets du moteur** (« Quand les réglages se rencontrent (2) ») : ce que lit la carte du cliquetis est dans `knockInputsOf` et `knockConditionsStock` (`combustion.cpp`) : un nouveau réglage qui change l'air, la came, la charge ou l'avance y entre, sinon la carte reste celle d'origine. Sur un quatre-temps à étincelle, la part de couple de l'avance passe par elle seule (`ecuAdvanceInKnockMap`). La chaleur latente vient de `fuelPropertiesOf` (`injectedFuelOf`), la part prise à l'air de `mixtureAirShare` : une nouvelle vaporisation les lit. `kTwoStrokeGeometricCompression` (`two_stroke.hpp`) est recopié dans `GEOMETRIC_COMPRESSION`, `kMaxTwoStrokeCylinders` dans `TWO_STROKE_MAX_CYLINDERS`. L'air du radiateur passe par `ThermalSpec::airPressureRatio`, la cible de pression par l'atmosphère du turbo ; les arbres du biturbo lisent l'air du jour de sa référence (`TwinTurboSpec::reference`, recopié dans chaque arbre par `halfTurbo`) ; sous régulation électronique ou selon le rapport, une seule électrovanne pilote leurs deux soupapes (ou les aubes), par un PID étalonné sur leur banc (`BoostControlSpec::twin`, `identifyTwinBoostPlant`), et un twincharger ne reçoit que sa cible (`TwinTurboInput::targetBar`). Le banc d'étalonnage attend que la pression ne bouge plus, faisceau stabilisé (`TurboInput::settledCooler`, `TwinTurboInput::settledCooler`) : sa masse thermique n'est pas la réponse de l'arbre. Le cycle de la came lit l'air du jour (`Geometry::airPa`, `airK`, `soundMs`), et ses tables ont l'air dans leur clé. La carte du cliquetis est tabulée à 90 et à 20 °C d'eau (`KnockMap::at(rpm, charge, eau)`). `usesTwinTurbo` est recopié sur le site ; `coherentConfig` y ramène l'anti-lag et le tube au défaut, comme `antiLagEngine_`. Le rupteur lit l'affolement de la came d'origine (`limiterRpmFor`), les culbuteurs le profil de la came (`camLobeOf`). Tant que l'eau est sous 70 °C, le ralenti accéléré a l'autorité du démarrage (`idleAuthority`).
- **Régulation de pression** : `kSpringBand` et `kSpringLeadS` de `boost_control.cpp` recopient `kWastegateBand` et `kWastegateLeadS` de `turbo.cpp` (`springGateDemand`, vérifiée au bit près par `boost_control_test.cpp`), et le test y recopie `kWastegateS` ; `kTyreGrip` de `DrivingModel` est passé à `boostControlSpecFor`. Télémétrie : `rf_boost_target`, `rf_boost_charge`, `rf_boost_duty` dans `exports.cpp`, `EXPORTED_FUNCTIONS`, `RfExports`, `Telemetry`/`IDLE_TELEMETRY` et `worklet.js` ; le canal `boostTarget` de `history.ts` retire `ATMOSPHERE_BAR`, la même atmosphère que `gaugeBar` en C++. Les colonnes ajoutées à `--trace` vont en fin de ligne.
- **Documents en deux langues** : `docs/modele.md` et `docs/model.md`, `README.fr.md` et `README.md` ont les mêmes sections, et un changement du modèle ou des limites connues va dans les deux.
- **Calculateur** (`ecu.hpp`, « Le calculateur » de `docs/modele.md`) : sa télémétrie `rf_ecu_*` (`exports.cpp`, `EXPORTED_FUNCTIONS`, `RfExports`, `Telemetry`/`IDLE_TELEMETRY`, `worklet.js`) et sa fiche (`Spec.ecu`). Il reprend des chiffres d'ailleurs, à tenir ensemble : la parabole (68°) et la part des parois (20 %) de `anti_lag.cpp` ; la richesse d'origine (0,88, 0,82) et la rampe de 85 % de `consumption.cpp` ; `torqueOfRichness` du carburateur ; la part qui brûle au collecteur (`kUnburntCollectorShare`, celle de `kCutBurnShare`) et `antiLagIgnition` ; la chance, la taille et les 90 J des détonations de la coupure de cylindres (`maybeEcuPop`, `engine_sound.cpp`) ; l'inertie des parois du gaz de sortie (`kPortHeatS`, `kPortCoolS`, celles de `kHeatUpS`, `kCoolDownS` de `turbo.cpp`), dont il lit le modèle par `exhaustHeatShare`. Une nouvelle coupure de combustion qui laisse passer le carburant renseigne `fuelOnCut_`, donc `burnt_.burning` et le gaz de la turbine ; une coupure d'injection partielle, `burnt_.fuelShare`. Le départ de la fiche (`measurePerformance`) passe par le launch control s'il est réglé, chronomètre au lâcher du frein, comme `--scenario launch_control` et le cas de `check_wasm.mjs`. `ShiftMode::Normal` et le trajet `City` restent ceux d'origine : le calculateur n'agit que réglé.
- **Lien de partage** : `encodeConfig`/`decodeConfig` sont positionnels, et les liens déjà partagés dépendent du format. La voiture et la pression du turbo suivent après un `~`, l'emplacement, l'isolation, les sorties et la taille du turbo après des `_` dans ce même groupe, la boîte après un second `~`, seulement si elle n'est pas celle par défaut ; le champ `multiplier` reste à sa place, ignoré, pour que les anciens liens restent valides. Les réglages du socle moteur suivent après un troisième `~` (un groupe de boîte vide s'il le faut : `…~voiture~~amb=35,flat=1`), en `code=valeur` séparés par des virgules, seulement ceux qui diffèrent du défaut : ce groupe n'est pas positionnel, un code inconnu ou une valeur invalide est ignoré, un nombre est ramené dans ses bornes. Les codes sont dans `TUNING_FIELDS` (`config.ts`) et ne changent jamais.
- **Air ambiant** : `ambientAirOf` (`core/src/atmosphere.cpp`) et sa recopie `web/src/lib/atmosphere.ts` (atmosphère type, kelvin du modèle 293 + (θ − 20), R = 287, 343·√θ) ; `ambientC` et `altitudeM` dans `gasKey`. Dans l'air de référence (20 °C, 0 m), chaque usage doit recevoir exactement son ancienne constante : `reference()` vrai, rapports δ, θ, σ, √θ exactement 1, et une branche qui saute le calcul là où une multiplication arrondirait autrement (`atmosphere_test.cpp` le vérifie). Ce qui est une pièce ou un étalonnage (turbo, compresseur, boîte, embrayage, convertisseur, carte de passage) se dimensionne sur `withReferenceAir` ; ce qui en tourne reçoit l'air du jour (`TurboSpec::ambientPa`, `ambientK`, `SuperchargerSpec`, `TurboPipeSpec::ambientK`, `airInletBehind`). Le son le reçoit par `CarAcoustics::air` (`airAcousticsOf`), et toutes les sources à 1 m y sont multipliées une fois par σ : une nouvelle source n'a rien à faire de plus. Les jauges `rf_turbo_*` lisent au-dessus de l'atmosphère du jour, et `Motion` en tire le rapport du compresseur.
- **Combustion** : les taux d'origine de `stockCompressionRatio` (combustion.cpp) sont ceux du démarreur (`EngineConfig::toProfile`, `rotaryCompressionRatio`), recopiés dans `stockRatio` (`SettingsCombustion.svelte`) et dans les appels de `compressionRatioOf` de `fluidGas.ts` ; ses bornes (14:1 en diesel, 11,9:1 sur un rotatif) aussi, et dans `ratioMin`/`ratioMax` du volet. La condition de `knocks` (`Dynamics.svelte`) recopie `combustionStock` et `knockConditionsStock`. La plage de l'essence (4 à 24:1) est dans `kRatioMin`, `LIMITS.compressionRatio` et les appels de `compressionRatioOf` de `fluidGas.ts`. Le calage de `KnockMap::Inputs::ivcAbdcDeg` (50° après le point mort bas) et les 40° d'arbre du rotatif suivent `kIvc` et `kPortIvc` d'`engine_sound.cpp`. Le cliquetis va au son par `setKnock(model.knockDrive())`, dans `play()` de la CLI et `advance()` d'`exports.cpp`. Sa télémétrie : `rf_spark_advance`, `rf_knock_limit`, `rf_knock_retard`, `rf_knock_share` dans `EXPORTED_FUNCTIONS`, `RfExports`, `Telemetry`/`IDLE_TELEMETRY` et `worklet.js` ; sa fiche : `rf_compression_ratio`, `rf_compression_efficiency`, `rf_knock_margin_deg`, `rf_knock_margin_rpm`, `rf_knock_sensor`, dans `Spec.combustion`. Le SP95 de `fuelProperties` garde les chiffres de `kPetrol` (`consumption.cpp`), vérifié par un test.
- **Injection** (`core/src/injection.cpp`, `particulate_filter.cpp`, `injector_sound.cpp`, voir « L'injection » dans `docs/modele.md`) : `fuelSystemOf` rend l'alimentation réelle, `Direct` compris ; ce qui veut un carburateur teste `hasCarburetor`. Le film d'Aquino (`WallFilm`) est partagé par `Carburetor` et `PortFuelFilm`. Où vaut chaque réglage : `directInjected`, `commonRailed`, `recirculated` (pas sur un rotatif), `particulateFiltered` (diesel ou injection directe), recopiés par les conditions de `SettingsFueling` et par `filtered` dans `GaugeBank`. La température d'eau entre par `DrivingModel::setCoolantC` et `CarburetorInput::coolantC` (90 °C, `kWarmCoolantC` : à cette valeur, rien ne s'exécute) ; `updateColdEffects` y met toujours l'eau du réseau thermique, et `setCoolantC` ne tient que sur un modèle tenu à la référence (`holdThermalReference`). La fiche : l'ordre des chiffres de `rf_injection_figure` est celui de `Spec.injection` (`engine.ts`). La télémétrie : `rf_dpf_load`, `rf_dpf_kpa`, `rf_dpf_regen`, `rf_dpf_c`, `rf_egr_share`, avec `Telemetry`/`IDLE_TELEMETRY` et `worklet.js`. La post-injection passe par `burnt_.extraFuelGps`, avec l'anti-lag. Dans le son, `filterResistance` entre dans `sameParts` (la ligne se recalcule), et les niveaux du tic (`kNeedleShare`, `kPumpShare`) sont calés sur SAE 2011-01-0930 : à recaler si le plancher du bloc change.
- **La came** (`core/src/cam.cpp`, docs « La came ») : la loi de levée, `makeCamProfile`, `camProfileOf`, `highCamProfileOf` et leurs constantes (`kCamStockDurationDeg`, `kCamStockLobeSeparationDeg`, `kCamTwoStepSpreadDeg`, `kCamTwoStepLiftSpread`, `kCamPhaserAuthorityDeg`, `kHalfSpanMaxDeg`, `kLiftPerBore`) sont recopiés dans `web/src/lib/cam.ts`, que `came.spec.ts` compare au WASM (`rf_cam_spec`). Le gaz à l'écran (`EVO`… de `fluidGas.ts`) et le dessin (`EngineLayout.timing`, levée des bossages) ajoutent à leur calage d'origine ce que la came change (`camShift`) : rien sur la came d'origine, d'où les mêmes chiffres qu'avant. Le son part de `kEvo`… tant que `EngineProfile::camTuned` est faux, et les champs `cam*` du profil sont remplis par `applyCam`. `camKey` entre dans `layoutKey` et `gasKey`. Fiche et télémétrie : `rf_cam_spec`, `rf_cam_high`, `rf_cam_phaser` dans `exports.cpp`, `EXPORTED_FUNCTIONS`, `RfExports`, `Spec.cam`, `Telemetry`/`IDLE_TELEMETRY` (`camHigh`, `camPhaser`) et `worklet.js`. `EngineSound::setCam` reçoit `DrivingModel::camDrive()` dans `cli/render.cpp` et `exports.cpp`. Les gaz résiduels du son (`kCamBackKpa`, `kCamIdleLoad`) recopient la contre-pression de `cam.cpp` et le remplissage du modèle de conduite au ralenti.

`presets/presets.json` est la source unique des préréglages : CMake le convertit en `presets_data.inc` via `scripts/gen_presets.py`, et le site l'importe directement. Ne pas écrire de préréglage ailleurs.
