# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Revforge simule en temps réel une voiture et le son de son moteur, tous deux configurables : un cœur C++20 sans dépendance, joué dans le navigateur via WebAssembly, ou rendu en WAV en ligne de commande. Les commentaires, les noms de tests et les messages de commit sont en français ; les identifiants, la CLI et le texte par défaut du site sont en anglais.

## Commandes

Il faut CMake, Ninja, Python 3 (génération des préréglages), GCC ou Clang (les options de déterminisme de `CMakeLists.txt` sont les leurs) et, pour le WASM, Emscripten et Bash. Si `node`/`npm` sont introuvables, charger Emscripten, qui les fournit : `source ~/emsdk/emsdk_env.sh`. `scripts/build_wasm.sh` lit aussi `EMSDK` s'il est installé ailleurs.

```bash
# Natif (ctest ne recompile pas : toujours construire avant)
cmake -S . -B build -G Ninja && cmake --build build
ctest --test-dir build --output-on-failure
ctest --test-dir build -R golden_                  # empreintes seules
./build/revforge_tests -tc="pas de clic*"          # un test doctest

# WebAssembly (compile et copie vers web/public/revforge.wasm, ignoré par git)
scripts/build_wasm.sh
node tools/check_wasm.mjs build-wasm/revforge.wasm build/revforge-render

# Site, depuis web/
npm ci
npm run dev
npm run check                                      # svelte-check, seul contrôle de types
npm run build && npx playwright test               # une première fois : npx playwright install chromium firefox
npx playwright test -g "exporte un WAV valide" --project=chromium
```

`revforge_tests` dure plusieurs minutes, les empreintes moins d'une demi-minute. Un filtre doctest qui ne trouve rien affiche quand même `Status: SUCCESS` : regarder `test cases`. Sous Windows, un filtre accentué ne trouve jamais rien : mettre un joker à la place du mot accentué.

Playwright teste `vite preview`, donc `web/dist` : sans `npm run build` (et `scripts/build_wasm.sh` si le C++ a changé), il teste l'ancienne version. Il réutilise aussi un serveur déjà lancé sur le port 4173 (`REVFORGE_PW_PORT` en choisit un autre).

La CI (`.github/workflows/ci.yml`) enchaîne tout cela sous Ubuntu. `pages.yml` publie le site à chaque push sur `main`, sans attendre la CI, dans un sous-dossier, d'où `base: './'` dans `vite.config.ts`. L'`AudioWorklet` n'existe qu'en contexte sécurisé : `web/index.html` redirige le HTTP vers le HTTPS, sauf en local et sur une adresse IP, et un téléphone sur `http://<IP>` n'a donc pas de son.

Pour la consommation, sans rendre de son : `./build/revforge-render --out none --preset city_14 --scenario wltc --fuel 1` (aussi `cruise --kmh 90` et `idle`). Pour le creux de reprise d'un carburateur : `--out none --carb single --scenario tipin --rpm 1500`.

Pour écouter ou comparer un rendu : `./build/revforge-render --list`, `--help` pour les options, `--scenario turbo` pour le retard (avec `--preset`, seuls `--exhaust`, `--routing`, `--supercharger`, `--antilag`, `--turbo-pipe`, `--cam`, `--filter`, `--carb` (ou `--fuel-system`), les réglages du socle moteur (`--help`, de `--cycle` à `--start`), l'emplacement, l'isolation, les vitres et les options de boîte s'appliquent, celles-ci remplaçant toute la boîte du préréglage, et `--stroke`, sur l'alésage et les cylindres du préréglage ; le reste est ignoré : donner tout le moteur pour changer `--turbo` ou `--layout`), `tools/compare_wav.py a.wav b.wav`. Pour mesurer un rendu face à de vrais moteurs : `tools/analyze_sound.py --png sortie.png a.wav b.wav` (numpy, scipy et matplotlib requis) ; regarder le spectrogramme, car un spectre moyen ne révèle pas un défaut temporel. Pour un sifflement de boîte : `tools/analyze_gearbox.py fichier.wav:début:fin:f1min:f1max`. Pour les rangs d'un régime tenu, en ordres de l'arbre : `tools/analyze_orders.py --rpm 4000 a.wav b.wav`.

## Architecture

Une seule simulation, `core/`, trois façons de l'appeler : `cli/render.cpp`, `tests/`, et `wasm/exports.cpp`, une interface C à état global (`rf_*`).

- `EngineSound` (`core/src/engine_sound.cpp`) : le son, échantillon par échantillon, à partir d'un `EngineProfile`, d'un régime et de `setDrive` (remplissage, turbo, coupure). Sans `setDrive`, la charge se déduit de la pente du régime, chemin utilisé par les tests et `--scenario steady`. Le modèle acoustique et sa calibration sont décrits dans `docs/modele.md`.
- `SoundField` et `CabinPath` (`core/src/acoustics.*`) : de la voiture à l'oreille. Les sources (`Source`) arrivent en pascals, à 1 m d'elles, placées par `carAcousticsOf` ; le chemin (directivité, caisse, air, retard, sol, tête ou parois) découle de ce plan, sans gain saisi par position. `SoundSheet` (`sound_sheet`) : les niveaux de fiche d'un réglage. Voir « D'où l'on écoute » dans `docs/modele.md`.
- `Powertrain` (`powertrain`) : `EngineConfig`, `CarConfig` et électrique ou non. C'est la source des courbes de couple, de la démultiplication et des performances ; rien de tout cela n'est saisi à la main.
- `GearboxConfig` (`gearbox`) : la boîte comme pièce, indépendante du moteur. `designGearbox` en tire les dents, les rapports, les inerties et le couple admissible ; `gearingOf` l'adapte à la voiture si le pont n'est pas choisi. Son bruit est `GearboxSound` (`core/src/gearbox_sound.cpp`) : des forces sur les roulements, à travers le carter, à partir de `GearboxDrive`. Il suit les arbres, jamais le régime du moteur, a son propre générateur, et reste muet sans `setGearbox`. Voir « La boîte » dans `docs/modele.md`.
- `ValvetrainParts` et l'affolement (`valve_float`) : les pièces de chaque distribution ramenées à la soupape, le ressort d'origine dimensionné pour la zone rouge, le régime d'affolement (`valveFloatRpm`) et ce qui se passe au-delà : remplissage (`valveFloatShare`, dans `breathing`), frottement de came des culbuteurs et des ressorts raides. Le son le reçoit par `EngineProfile::valves` ; ses deux bruits, le choc des poussoirs et le siège qui claque, sont `ValvetrainSound` (`core/src/valvetrain_sound.cpp`), chacun à son générateur, muets sans leur cause. Voir « Les culbuteurs et l'affolement » dans `docs/modele.md`.
- `Carburetor` (`carburetor`) : un col et une pipe communs, ou un corps par cylindre, selon `FuelSystem`. `carburetorDropPa` donne la perte de charge, appliquée dans `breathing` ; `Carburetor::step` suit le carburant (colonne, pompe, film x-τ) à chaque pas de `DrivingModel`, et renvoie la part du couple que permet le mélange. Tout cela ne s'exécute pas sur une injection, ni sur un diesel, qui l'ignore. Voir « Le carburateur » dans `docs/modele.md`.
- `TurboCharger` (`turbo`) : l'arbre du turbo, intégré à chaque pas de `DrivingModel` par son bilan de puissance, sans constante de temps de retard. `boost()` est la pression réelle avant le papillon, en part de `boostBar`, et `torqueCurveNm` en est l'équilibre (`turboSteady`). Le son le reçoit par `setTurbo` ; le gaz (`fluidGas.ts`) en suit le rapport de pression et la sortie du compresseur : il n'y a qu'un turbo. Sur un moteur sans turbo, rien de tout cela ne s'exécute. L'anti-lag (`anti_lag.cpp`) ne change que ce qui arrive à la turbine, pied levé, sur un turbo à essence ; `--trace` en écrit les chiffres.
- `Supercharger` (`supercharger`) : le compresseur mécanique, à un rapport fixe du vilebrequin. Un volume entre lui et le papillon, sans arbre à lancer ; `superchargerSteady` en est l'équilibre, et ce qu'il prend au vilebrequin se paie à part (`driveNm`). Il passe par les mêmes `rf_turbo_charge`, `rf_turbo_out_c`… que le turbo. Son bruit est `SuperchargerSound` (`core/src/supercharger_sound.cpp`) : des poches qui se vident, à son propre générateur.
- `DrivingModel` : intègre à pas fixe de 1 ms le couple, l'inertie, l'embrayage, la boîte et les pneus. Il pilote le son avec le régime *réel* du moteur. Sa logique de passage (`shift_logic.cpp`, fonctions pures) et ses trajets (`driver_scenarios.cpp`, des données) sont à part : `docs/modele.md`. Le mode normal et le trajet `City` sont la logique d'origine, au bit près : le mode normal sur route plate ne passe pas par `decideShift`. `EngineProfile::fromCarRpm` et `revMultiplier` ne servent plus qu'à une source de régime externe (bus CAN) : le site et les scénarios modélisés ne les utilisent pas.
- `ConsumptionMeter` (`consumption`) : essence, huile ou énergie, intégrées à chaque pas de `DrivingModel` à partir de ce que fait le moteur (bilan d'énergie, `docs/modele.md`, « La consommation »). Il lit le couple et ne renvoie rien vers la physique : la masse ne baisse pas, le son ne change pas.

Côté site, `web/src/lib/engine.ts` instancie **deux exemplaires** du même WASM : l'un dans l'AudioWorklet (`web/public/worklet.js`, JS pur, ni compilé ni typé) pour le son, au taux de l'`AudioContext` ; l'autre sur le thread de la page pour la fiche technique (`Engine.spec`) et l'export WAV, à 44,1 kHz. La page pilote le worklet par messages, et il renvoie sa télémétrie à 30 Hz. Les vues animées (`CarStage`, `EngineView`, `ExhaustView`, `GearboxView`) sont des canvas qui partagent une seule horloge, `Motion` (`web/src/lib/motion.ts`), réglée sur la télémétrie : ralenti réglable (`motion.slow` : 12 par défaut, 4, ou 1 pour le temps réel), proportionnel au vrai régime et sans plafond, une bouffée par explosion dans l'ordre d'allumage. Une nouvelle animation lit cet état au lieu d'avoir sa propre horloge.

La couleur du thème est une chaleur : `web/src/lib/heat.ts` traduit la température des parois (`Motion.heat`, temps réel, jamais celle du gaz, qui suit le ralenti) en `--heat`, `--heat-text`, `--on-heat`, à 8 Hz au plus et sur les seuls éléments marqués `use:heated`, jamais sur la racine. Le reste de la page reste neutre et se sépare par le ton, sans bordure ; une voiture électrique garde une couleur froide fixe, sans chaleur inventée.

La page est un tableau de bord sur toute la largeur (`App.svelte`) : poste de conduite à gauche (`Tachometer`, démarrage, pédales, modes), voiture et une seule vue à la fois au centre, jauges à droite (`GaugeBank`, `PowerCurves`, `LevelMeter`), `Dynamics`, `Trends` et `Spectrum` dessous, `ChartsPanel` à la demande. Sur téléphone, le démarrage et les pédales se collent au bas de l'écran. Une vue (`EngineView`, `ClutchView`, `GearboxView`, `ExhaustView`) est montée la première fois qu'on la demande, puis cachée et en pause. Les réglages sont dans des volets (`Panel.svelte`, un `<dialog>` non modal ouvert par `show()`) : le reste de la page reste vivant, et les pédales restent cliquables. Ils restent montés quand ils sont fermés, donc ce qui lit la télémétrie à l'intérieur reçoit `IDLE_TELEMETRY` ou 0 volet fermé. Une jauge n'est jamais un composant rendu à 30 Hz : `Gauge` et `Meter` écrivent dans le DOM via une `InstrumentClock` (`lib/instruments.ts`), seulement ce qui a changé. Ils lisent `Readings`, qui lit la télémétrie et le modèle du gaz ; `motion.update(…, false)` sert aux jauges qui n'ont pas besoin du gaz, pour qu'il ne soit calculé que si une vue ou une jauge qui le montre est à l'écran. Animations coupées, `Motion.meters` fait avancer un réseau à part pour ces jauges, sans panache ni particules. Une jauge ne montre que ce que la simulation calcule : rien d'inventé.

La vue de la boîte (`GearboxView`) a trois couches sans DOM ni WebGL, testées sans navigateur : `gearboxModel.ts` (quelles pièces, où, comment elles tournent, à partir de `BoxSpec`), `gearboxGeometry.ts` (maillages : dentures en développante, hélice), puis `gearboxPaint2d.ts` et `gearboxScene.ts` pour dessiner le même état en coupe 2D ou en 3D. Le primaire vient de `Motion` et tout le reste s'en déduit par les dents, ce qui garde les paires en prise. Une automatique y est un schéma, le simulateur n'ayant pas de train épicycloïdal.

`EngineView` dessine en 3D (three.js, chargé à la demande par `render3d.ts`) ou en écorché 2D (`engine2d.ts`) le même moteur : `engineLayout.ts` déduit de l'ordre d'allumage et de l'architecture la place de chaque cylindre et les angles du vilebrequin, `EnginePose` calcule à chaque image ce que lisent les deux vues, `turboChain.ts` place pour elles le chemin de l'air d'un turbo, `engineScene.ts` construit les pièces 3D. `mesh3d.ts` génère les maillages, sans dépendance ; `threeSubset.ts` liste ce que le site utilise de three.js, pour que le reste ne soit pas livré. Sur un rendu logiciel, `render3d.ts` remplace le PBR par des matcaps et le verre par des arêtes. Un rotatif a ses propres pièces, sans rien de tout cela : `rotary.ts` (géométrie, `RotaryPose`, testés sans navigateur), `rotary2d.ts`, `rotaryScene.ts`. `GasNetwork` y calcule trois chambres par rotor, sur 1080°.

Le texte du site passe par `web/src/lib/i18n.svelte.ts` : `t`, `whole` et `fixed` suivent la langue courante (anglais par défaut, français au choix, jamais celle du navigateur), en direct dans les gabarits et à chaque image dans les canvas, sans jamais toucher au son.

Le gaz à l'écran (`web/src/lib/fluid*.ts`) est un vrai calcul, mais pour l'affichage seulement : il suit `Motion`, en temps physique divisé par `motion.slow`, et n'agit jamais sur le son. `GasNetwork` (`fluidGas.ts`) : Euler quasi-1D à section variable pour les tubes (volumes finis, flux HLLC), bilans à zéro dimension pour les cylindres (remplissage et vidange, combustion de Wiebe) et les volumes de jonction. `FluidField` (`fluidField.ts`) : stable fluids 2D, pour le panache et la recirculation dans les volumes, pilotés par l'état du réseau. `GasFlow` (`fluid.ts`) assemble le tout avec les particules, la qualité adaptative et le sommeil moteur coupé ; `GasPainter` (`fluidRender.ts`) dessine. Rien de cela n'utilise WebGL. L'embrayage (`ClutchView`) lit la télémétrie, avec son échauffement dans `Motion` : `clutchMechanism.ts` calcule sans rien dessiner la chaîne pédale, hydraulique, fourchette, butée, diaphragme, plateau, et la bague de la butée (`Motion.releaseRace`) ; `clutchSection.ts` donne en millimètres les profils que `clutchDraw2d.ts` coupe et que `clutchScene3d.ts` tourne, sur la scène de `render3d.ts`. La levée du plateau est dessinée agrandie (`LIFT_EXAGGERATION`, indiquée à l'écran), jamais calculée ainsi. Les graphiques (`ChartsPanel`) ne sont montés que panneau ouvert ; `history.ts` remplit en permanence un anneau de mémoire fixe.

## Invariants

**Déterminisme au bit près.** Natif et WASM produisent le même son, vérifié par `check_wasm.mjs`. La parité avec la version Kotlin d'origine (CANCitroen) a été abandonnée volontairement lors de la refonte du son. Dans le son, passer par `revforge::km` (`core/src/kotlin_math.hpp`, calcul en `double` arrondi en `float`) et garder conscience de l'ordre des appels à `random()` : ajouter un tirage décale tout le son qui suit, donc les empreintes. Dans `DrivingModel`, passer par `revforge::portable` (`core/src/portable_math.hpp`) plutôt que par les fonctions de la bibliothèque mathématique autres que `sqrt` : leurs résultats diffèrent d'un dernier bit entre plateformes, et cet écart s'amplifie jusqu'à décaler un passage de rapport.

**Changer le son est un choix.** Les tests `golden_*` de `CMakeLists.txt` comparent un hachage du rendu 16 bits. Si un changement est voulu, reprendre la nouvelle valeur affichée par `revforge-render --out - <arguments du test>` et la mettre à jour ; sinon, c'est une régression. Modifier un préréglage utilisé par ces tests change aussi leur empreinte. Les mesures spectrales ne suffisent pas à valider un son : l'écoute tranche, et il faut le signaler quand elle reste à faire. Un test de son doit être contre-éprouvé en retirant ce qu'il protège : c'est ainsi qu'un premier test anti-« fermeture éclair » s'est révélé aveugle.

**Tout ce qui ne vient pas de l'échappement garde sa place à bas régime.** L'échappement varie beaucoup avec la charge ; une source à niveau fixe (soupapes, par exemple) passe devant dès qu'il se fait discret. C'est ainsi qu'est né le défaut « métal qui claque ». De même pour un souffle : à pleine bande et à niveau presque fixe, il reste derrière le moteur comme un bruit blanc, d'où `kNoiseTopHz`. Le comparateur ne voit pas ce défaut : mesurer la bande 8-16 kHz face à 500-2000 Hz, et se méfier des références, dont un « ralenti » s'est révélé être un moteur coupé. Un nouveau bruit a sa place sur la voiture : `stem(Source::…)`, en pascals à 1 m, à un seul endroit.

**Le niveau est physique, de bout en bout.** La réponse de la ligne n'est pas normalisée, et aucun réglage ne compense d'une position ou d'un échappement à l'autre : c'est ainsi qu'une ligne directe avait fini moins forte qu'une ligne d'origine. Une ligne, une isolation ou une position qui changent le niveau doivent le faire par leur géométrie ; seul `toneGain`, après le sonomètre, ramène le niveau réel vers la sortie. Le dB(A) affiché est lu avant le volume, et reste une estimation, jamais présentée comme mesurée. Tenir aussi `tests/acoustics_test.cpp` face aux valeurs publiées : ne pas corriger un écart de niveau en touchant à une formule.

**Pour un bruit mécanique, partir d'enregistrements et de la cause.** Le démarreur a été rejeté cinq fois à l'écoute alors que rythme et spectre moyen étaient justes : sinusoïdes (« vaisseau »), chocs aléatoires sur résonances molles (« cailloux »), frottement sur résonances fines (« ballon en latex »), note forte qui glisse à volume constant (« DJ qui fait drifter un CD »). Des sons générés (ElevenLabs) peuvent servir de référence d'écoute, jamais de son livré : le son du site reste simulé. Il est calé sur de vrais démarrages (`tools/analyze_starter.py`, `docs/modele.md`) : couple transmis calculé par `compressionLoadNm`, et dans `StarterSound` (`core/src/starter_sound.cpp`) un bruit de contact selon le couple, des balais selon le courant et des chocs d'engagement, le tout passé dans une réponse dense propre au moteur. Comparer des spectrogrammes en fenêtres courtes : une longue fenêtre cache les raies qui ondulent.

**Le timbre ne suit pas le régime.** La ligne (`ExhaustLine`, réponse calculée depuis sa géométrie, convolution partitionnée) est fixe : ce sont les harmoniques qui défilent devant. Tout le gaz la traverse. Les raies doivent s'effacer progressivement vers les aigus sans disparaître : de 8,7 à 17,1 dB entre 1,5 et 3,5 kHz sur de vrais moteurs. Trop, c'est la « fermeture éclair » ; trop peu, c'est du bruit sans moteur (`tools/perceptual_compare.py`).

**La consommation lit, elle n'écrit pas.** Aucun chiffre de consommation ne revient vers le couple, la vitesse ou le son. Ne pas régler un préréglage pour coller à un chiffre publié : l'écart se montre dans le tableau de `docs/modele.md`. L'huile reste un ordre de grandeur, à un facteur trois près ; ni niveau, ni pression, ni température d'huile tant qu'ils ne découlent de rien de réel.

**Temps réel.** `EngineSound::render` n'alloue pas et ne prend aucun verrou (vérifié par un test via `operator new`, dans `tests/main.cpp`). Le résultat ne dépend pas de la taille des blocs : tout état doit évoluer par échantillon, pas par bloc.

**Contraintes du WASM.** Pas d'exceptions ni de RTTI, 4 Mo de mémoire sans croissance, et aucun import : le worklet instancie le module avec `{}`, donc une fonction qui tire un import système casse le chargement.

**Le gaz à l'écran n'alloue pas.** Viser moins de 4 ms par image pour tout le fluide. Dans `fluid*.ts`, jamais de nombre à virgule en argument d'une fonction que le compilateur ne déplie pas, ni de `let` de module : cela alloue un objet par appel, 85 ko par image sur une première version. Passer par les tableaux (`riemann`, `flux`, `orifice`, `reservoir`) et les champs de la classe. Les pas de calcul lisent leurs entrées dans `FrameInputs`, recopié une fois par image : lus sur des objets de formes diverses, ses nombres sont recopiés à chaque lecture (3 ko par image de plus, et `interface.spec.ts` échouait en CI une fois passés les tests de nouveaux réglages). Un test mesure le tas, dans l'état où l'ont laissé les spécifications précédentes : en lancer une seule ne suffit pas. Un test de physique compare aussi une onde au coefficient de réflexion théorique : ne pas remplacer le calcul des changements de section (`stepAreaChanges`) par un flux direct entre cellules, qui invente 0,3 bar de contre-pression par volume.

## Ce qui doit rester synchronisé

Rien ne génère ces correspondances, et un oubli peut passer inaperçu à la compilation :

- **Nouvelle fonction `rf_*`** : `wasm/exports.cpp`, `EXPORTED_FUNCTIONS` dans `CMakeLists.txt`, `RfExports` dans `engine.ts`, et `worklet.js` si le worklet doit l'appeler (commande ou télémétrie).
- **Valeurs d'une énumération** : les énumérations C++ (`engine_config.hpp`, `powertrain.hpp`), les tables de `scripts/gen_presets.py`, les options de la CLI, et les tableaux de `web/src/lib/config.ts`, dont **la position** donne la valeur envoyée au C++ (`configArgs`, `carArgs`) : les réordonner change le moteur demandé. `ShiftMode`, `DriveScenario` et `LegKind` suivent la même règle : `shift_logic.hpp` et `driver_scenarios.hpp`, `SHIFT_MODES`, `DRIVE_SCENARIOS` et `LEG_KINDS` dans `config.ts`, avec leurs textes `shiftMode.*`, `scenario.*` et `leg.*`, et les codes de `check_wasm.mjs`. Ce sont des choix de conduite : ils restent hors du lien de partage. `Listener` est aussi recopié dans `engine.ts`. Les codes écrits en dur dans `tools/check_wasm.mjs` aussi.
- **Arguments de `rf_set_config`, `rf_set_car` et `rf_set_gearbox`** : `exports.cpp`, `configArgs`/`carArgs`/`gearboxArgs`, et les appels de `check_wasm.mjs`, qui recopient aussi les réglages des préréglages comparés (les supercars ont un double embrayage).
- **La boîte** : `GearboxKind`, `GearFamily`, `ToothForm`, `Flywheel` dans `gearbox.hpp`, les tables de `gen_presets.py`, `--gearbox` et ses voisines dans la CLI, `BOX_KINDS`, `BOX_FAMILIES`, `BOX_TEETH`, `BOX_FLYWHEELS` dans `config.ts`, où la position donne la valeur. Les champs `box*` des préréglages sont optionnels : absents, ils prennent les défauts de `GearboxConfig`, de `DEFAULTS` et de `gen_presets.py`.
- **Valeurs par défaut d'un moteur** : `EngineConfig` en C++, `DEFAULTS` dans `config.ts` et `gen_presets.py`. Les champs moteur absents de `presets/presets.json` les prennent ; la voiture, elle, y est toujours écrite en entier.
- **Dimensions d'une carrosserie** : `BodySpec` en C++ pour la physique, `SHAPES` dans `CarStage.svelte` pour le dessin, `LINE_SCALE` dans `fluidGas.ts` : `retro.spec.ts` les compare. `Body` suit aussi la règle des énumérations (`BODY` de `gen_presets.py` et `check_wasm.mjs`, `--body`, `BODIES`). `insulation`, dans `BODIES`, n'existe que sur la carrosserie qui impose la sienne.
- **Géométrie de la ligne à l'écran** : `LINE_SECTIONS` et `LINE_SCALE` dans `fluidGas.ts` recopient `kStock`, `kSport`, `kStraight` (`exhaust_line.cpp`) et `BodySpec::exhaustScale`. `headerLength` reprend les ordres de grandeur de `EngineConfig::toProfile`. Une erreur n'y change pas le son, seulement ce qu'on voit.
- **Télémétrie de l'embrayage** : `clutchInputRpm`, `clutchSlipKw`, `clutchTorque` dans `Telemetry` et `IDLE_TELEMETRY` (`engine.ts`), `worklet.js`, et `rf_clutch_*`. Le niveau `levelDbA` (`rf_level_dba`) suit le même chemin et alimente aussi la courbe de `history.ts`.
- **Couleurs des graphiques** : `seriesStyle` dans `ChartsPanel` et les `light-dark()` de `ChartsPanel`, `ChartsLine`, `ChartsSpectrogram` sont validées contre `--surface` (`validate_palette.js` du skill dataviz). À revalider si le fond change.
- **Échappements** : `kStock`, `kSport`… dans `core/src/exhaust_line.cpp` (qui font le son) et `EXHAUST_LINES` dans `web/src/lib/exhaustLines.ts` (qui fait le dessin, et le gaz à l'écran).
- **Positions et sources** : `Listener` en C++ et dans `engine.ts`, les arguments de `--listener` dans la CLI, `presetPoint` dans `ListenerPanel.svelte` (à recaler sur `applyListenerPreset`), et les codes de `check_wasm.mjs`. `Source` : `rf_source_*` et `CabinPath::groupOf`.
- **Texte visible** : toute nouvelle chaîne, y compris `aria-label`, `title` et texte de canvas, va dans `web/src/lib/locales/en.ts` et `fr.ts` ; `npm run check` refuse une clé absente de l'un des deux. Dans un tableau de `config.ts` ou d'un composant, le texte est un accesseur (`get label() { return t('…'); }`), relu à l'affichage. Un préréglage a son anglais dans `presets/presets.json` et son français dans `frPresets` (`fr.ts`), par identifiant. Les spécifications Playwright lisent le français grâce au `storageState` de `playwright.config.ts`, sauf `i18n.spec.ts`, qui balaie la page anglaise à la recherche de français oublié.
- **Calage et démarreur de la vue du moteur** : `EVO`, `EVC`, `IVO`, `IVC` de `fluidGas.ts` doivent rester proches de `kEvo`… de `engine_sound.cpp` (`moteur.spec.ts` le vérifie à 10° près) ; `starterTeeth` dans `engineLayout.ts` recopie `EngineConfig::toProfile`.
- **Moteur rotatif** : `kPortEvo`… de `engine_sound.cpp` et `SHAFT_EVO`… de `rotary.ts` (`rotatif.spec.ts` les compare) ; les proportions et les taux de `engine_config.cpp` et de `rotaryShape`, `rotaryCompression` ; `sweptCcPerTwoTurns` et `firingsPerTwoTurns` en C++, `sweptCc` et `firingsPerCycle` sur le site. Un réglage qui n'a pas de sens sur un rotatif teste `isRotary`, et `coherentConfig` (`config.ts`) ramène ce qui n'existe pas à ce qui existe.
- **Ordres d'allumage** : `placementOf` dans `engineLayout.ts` dit sur quelle rangée va chaque numéro de `FIRING_ORDERS` ; changer un ordre sans le placement donne un vilebrequin qui n'existe pas (`moteur.spec.ts`).
- **Nouveau réglage ou nouveau volet** : le réglage va dans son volet (`EngineSettings`, `ExhaustSettings`, `GearboxPanel`, `CarSettings`, `ListenerPanel`, ou directement dans `App.svelte`), et ce qu'il change dans le résumé du bouton (`summaries` dans `App.svelte`, une ligne `part(…)` par réglage). Le volet du moteur est fait de sections, une par fichier : `SettingsBlock` (architecture et cycle), `SettingsCombustion`, `SettingsValvetrain` (distribution, absente d'un rotatif ou d'un deux-temps), `SettingsFueling` (alimentation), `SettingsCharging` (suralimentation), `SettingsEcu` (calculateur) ; celui de la voiture finit par `SettingsConditions`. Chacune s'ouvre par `SettingsSection` (titre, `data-testid="section-…"`) ; un nombre dont 0 veut dire « d'origine » ou « sans » passe par `TunedSlider`, un réglage tout ou rien par `ON_OFF`. Un nouveau volet s'ajoute aussi à `PANEL_IDS`, `PANEL_LABEL`, et à `PanelId` dans `web/tests/aide.ts`.
- **Lecture de consommation** : `ConsumptionMeter`, les `rf_*` de `exports.cpp`, `EXPORTED_FUNCTIONS`, `RfExports` et `Telemetry`/`IDLE_TELEMETRY` dans `engine.ts`, `worklet.js`, et les chiffres comparés par `check_wasm.mjs` (ligne `raw` de `--fuel 1`). Une nouvelle coupure de combustion (`cut_`) ou une nouvelle source de couple dans `updateEngine` doit aussi renseigner `burnt_`.
- **Anti-lag** : `AntiLag` en C++, `ANTI_LAGS` dans `config.ts` (position), `ANTI_LAG_CODE` dans `fluidGas.ts`, `--antilag`, et les codes de `check_wasm.mjs`. Le motif `antiLagFires` (`anti_lag.hpp`) est recopié dans `fluidGas.ts`, et les allumages tardifs (`kRetardDeg`, `kAirRetardDeg`) dans `ANTI_LAG_LATE_*`. Sa télémétrie : `rf_antilag_*`, `EXPORTED_FUNCTIONS`, `RfExports`, `Telemetry`/`IDLE_TELEMETRY` et `worklet.js`. Une nouvelle coupure de combustion dans `updateEngine` doit aussi arrêter l'anti-lag.
- **Taille du turbo** : `TurboSize` en C++ et `gen_presets.py`, `--turbo` de la CLI, `TURBO_SIZES` dans `config.ts` (position), `TURBO_SCALE` dans `exhaustLines.ts` (recopie de `kSizeSmall` et `kSizeLarge`).
- **Réglages du socle moteur** (conditions, combustion, calculateur, alimentation, distribution, suralimentation, cycle : `ambientC` à `cycle`) : les champs ajoutés à la fin d'`EngineConfig`, dans cet ordre, et leurs énumérations (`StartTemp`, `FuelGrade`, `RevLimiter`, `TractionControl`, `DieselInjection`, `ValveTiming`, `ValveSprings`, `TurboLayout`, `BoostControl`, `Intercooler`, `EngineCycle`) ; `tuning()` dans `gen_presets.py` ; une ligne `later(&EngineConfig::…)` par option dans `cli/render.cpp`, posée après le préréglage ; `rf_set_tuning` dans `exports.cpp` et `EXPORTED_FUNCTIONS` ; `TUNING_FIELDS`, `tuningArgs`, `DEFAULTS`, `LIMITS` et les tableaux (`START_TEMPS`… `ENGINE_CYCLES`, position) de `config.ts` ; `TUNING`, `tune()` et les codes de `check_wasm.mjs`. `rf_set_tuning` ne reconstruit rien : il pose les réglages dans le moteur, et le `rf_set_config` ou le `rf_set_electric` qui suit les applique (comme `rf_set_gear_ratio` avant `rf_set_gearbox`), d'où un seul changement de moteur et jamais un moteur à moitié réglé ; `rf_set_config` garde ces champs et n'écrit que les siens. Le worklet reçoit `tuning` dans le même message que `config` ou `electric`. Ces correspondances sont vérifiées : l'ordre et les noms par `socle.spec.ts` (signature de `rf_set_tuning`, champs d'`EngineConfig`, `TUNING_FIELDS`) et par `check_wasm.mjs` (signature face à `TUNING`). Les valeurs ajoutées aux énumérations existantes (`Layout::Vr`, `Layout::W`, `Exhaust::Expansion`, `FuelSystem::Direct`) se comportent dans le socle comme `V`, `Straight` et `Injection`, partout où l'équivalente est lue (`case` voisins, `fuelSystemOf`, `EXHAUST_LINES`, `headerLength`, `POP_JOULES`…) : celui qui leur donne un sens retire cette équivalence. `Camshaft::Ohv` a le sien (« Culbuteurs et affolement » ci-dessous). Les textes de chaque sujet ont leur bloc à la fin d'`en.ts` et de `fr.ts` : on ajoute à la fin de son bloc.
- **Compresseur, anti-lag, tube du turbo, arbre à cames, filtre à air** : `SuperchargerKind`, `AntiLag`, `Camshaft`, `AirFilter`, `turboPipeMm` dans `engine_config.hpp`, les tables de `gen_presets.py`, `--supercharger`, `--antilag`, `--turbo-pipe`, `--cam`, `--filter` dans la CLI, `SUPERCHARGER_KINDS`, `ANTI_LAGS`, `CAMSHAFTS`, `AIR_FILTERS` dans `config.ts` (position), les arguments de `rf_set_config`, ceux de `check_wasm.mjs` et le lien de partage.
- **Course** : `displacementFor` et `STROKE_LIMITS` dans `web/src/lib/stroke.ts` (d'où viennent `LIMITS.strokeMm` et `LIMITS.displacementCc`), `displacementForStroke` en C++, `PISTON_SPEED_LIMIT` (recopie de `kPistonSpeedLimit`, vérifié par `course.spec.ts`), et les proportions dessinées par `engineLayout`, qui doivent couvrir tout ce que le curseur atteint.
- **Filtre à air** : `kStock`, `kPanel`, `kCone`, `kStacks` et `kBayRise*` dans `core/src/air_filter.cpp`, recopiés dans `AIR_FILTER_GAS` et `BAY_RISE_K` (`fluidGas.ts`, le gaz à l'écran) ; `stackLengthM`, recopié dans `stackLengthMm` (`engineLayout.ts`, le dessin) ; `rf_intake_air_c` dans `Telemetry` et `worklet.js`. Une erreur n'y change que ce qu'on voit. Toute nouvelle entrée d'air d'un moteur suralimenté (compresseur) passe par `airInletBehind`.
- **Soupapes d'un simple arbre** : `valveTrainOf` (`core/src/valvetrain.cpp`) et `valveSizes` (`web/src/lib/valves.ts`, recopie vérifiée par `moteur.spec.ts`), que lisent `fluidGas.ts` et `singleCamValves` dans `engineLayout.ts`. `camshaft` est aussi dans `gasKey` et `layoutKey`. Le double arbre ne passe pas par ces calculs : le modèle d'origine en est un. Les constantes viennent de `tools/valve_filling.py`.
- **Culbuteurs et affolement** : `twoValves` (`valve_float.hpp`) et `twoValves` (`valves.ts`) disent qui a deux soupapes, simple arbre et culbuteurs ; `valveTrainOf` et `valveSizes` leur donnent la même section. Le rapport `kOhvRatio` (`valve_float.cpp`) est recopié dans `PUSHROD_ROCKER_RATIO` (`engineLayout.ts`, vérifié par `culbuteurs.spec.ts`). La came d'origine de `stockCamLobe` recopie `kLiftPerBore` (`valvetrain.cpp`) et `kEvo` à `kEvc` du son, la fermeture `kStockIvcDeg` recopie `kIvc` ; la came réglable passe par `camLobeOf`. La forme du choc des poussoirs recopie `kRockerQ` et `kRockerDecayS`, celle du claquement le tic du siège (`valveBand`) : leurs niveaux sont relatifs. `rf_valve_sheet(item)` (0 affolement, 1 masse, 2 et 3 ressort, 4 fréquence propre, 5 rapport) suit `Spec.valves` dans `engine.ts`. Le rupteur et la came lisent `valveFloatRpm`. Tout ce qui n'a pas de soupapes (rotatif, deux-temps) passe par `hasValves`.
- **Rencontres de réglages** : `tests/jonctions_test.cpp` et `web/tests/jonctions.spec.ts`, décrites dans « Quand les réglages se rencontrent » de `docs/modele.md`. Un nouveau réglage qui change des pièces entre dans `layoutKey`, `gasKey` et `rotaryKey`. Un nouveau débit d'air passe par `sweptCcPerTwoTurns`, une nouvelle dépendance à l'arbre à cames ou à l'alésage par `valvetrain()` ou `effectiveBoreMm()`, à cause du rotatif.
- **Type de compresseur** : `SuperchargerKind` en C++ et `gen_presets.py`, `--supercharger` de la CLI, `SUPERCHARGER_KINDS` dans `config.ts` (position), les lobes de `kRootsPulses`/`kScrewPulses` (`supercharger.cpp`, `supercharger_sound.cpp`) et de `chargerUnit` (`superchargerLayout.ts`). Le chemin de l'air à l'écran est `CHARGER_INTAKE` dans `fluidGas.ts`, de même volume que `chargeVolumeM3` en C++.
- **Alimentation** : `FuelSystem` dans `engine_config.hpp`, `FUEL_SYSTEM` dans `gen_presets.py`, `--carb` dans la CLI, `FUEL_SYSTEMS` dans `config.ts` (position), le dernier argument de `rf_set_config`, le dernier champ `_` du lien de partage. La règle de dimensionnement de `carburetorSpecOf` est recopiée dans `web/src/lib/carburetor.ts` : une erreur y change le dessin et le gaz à l'écran, pas le son.
- **Chemin de l'air d'un turbo** : la chaîne de `TURBO_INTAKE` dans `fluidGas.ts` (longueurs, sections, frottements) doit garder le même volume que `chargeVolumeM3` en C++, et le même ordre de perte que `kRatedCoolerBar`.
- **Tube du turbo** : 400 mm est la référence, codée dans `turboPipeSpecFor` (`turbo_pipe.cpp`), dans `fluidGas.ts`, `turboChain.ts` et `CarStage` ; le diamètre de `kPipeDiameterAt2L` recopie `pipeDiameter` de `fluidGas.ts` ; ce que le tube a en plus allonge `chargeVolumeM3` en C++ et la partie `hot` de `TURBO_INTAKE` à l'écran, de la même section.
- **Documents en deux langues** : `docs/modele.md` et `docs/model.md`, `README.fr.md` et `README.md` ont les mêmes sections, et un changement du modèle ou des limites connues va dans les deux.
- **Lien de partage** : `encodeConfig`/`decodeConfig` sont positionnels, et les liens déjà partagés dépendent du format. La voiture et la pression du turbo suivent après un `~`, l'emplacement, l'isolation, les sorties et la taille du turbo après des `_` dans ce même groupe, la boîte après un second `~`, seulement si elle n'est pas celle par défaut ; le champ `multiplier` reste à sa place, ignoré, pour que les anciens liens restent valides. Les réglages du socle moteur suivent après un troisième `~` (un groupe de boîte vide s'il le faut : `…~voiture~~amb=35,flat=1`), en `code=valeur` séparés par des virgules, seulement ceux qui diffèrent du défaut : ce groupe n'est pas positionnel, un code inconnu ou une valeur invalide est ignoré, un nombre est ramené dans ses bornes. Les codes sont dans `TUNING_FIELDS` (`config.ts`) et ne changent jamais.

`presets/presets.json` est la source unique des préréglages : CMake le convertit en `presets_data.inc` via `scripts/gen_presets.py`, et le site l'importe directement. Ne pas écrire de préréglage ailleurs.
